# Listen Together room server (GANASUNO protocol v1)
Python 3.10+; no pip packages required. On your own trusted server run `python rooms.py` (loopback HTTP, port 8765) behind an HTTPS reverse proxy with a valid trusted certificate. Alternatively run `python rooms.py --host 0.0.0.0 --port 8765 --cert /path/fullchain.pem --key /path/privkey.pem` on a trusted network. Android requires a trusted HTTPS endpoint, not self-signed certificates or cleartext HTTP. Never expose the development server directly to the public internet without a hardened reverse proxy, request/rate limits and access controls. No hosted endpoint or certificates are included. Use a private test network or VPN and trusted domain. The server holds ephemeral data in RAM, expires rooms after six idle hours, limits 100 rooms and 16 members per room. No user accounts, durable storage, or permanent block lists. Room code permits joining a pending queue by default; member tokens authenticate actions. Keep code private. Host removal does not prevent rejoining with the code; host approval is recommended. Host leaving ends the room unless host is transferred first. Only video IDs, names, position, and playback status are shared, not media, login data or credentials. Each participant independently needs authorized playback access. The server is not compatible with Metrolist.

Android Settings → Listen Together (self-hosted). Enter trusted HTTPS base URL and display name. Host creates a room, copies the invitation; friends enter URL and code. Approve friends via Members. Host turns on continuous broadcast, guest turns on Follow host (replaces queue). Use at normal speed, non-live tracks. The app polls every 3 seconds while room dialog is open and app is in foreground; backgrounding suspends polling and resumes on return. When the host has not published for 15 seconds, server state becomes paused. This is approximate sync, not gapless or sample-accurate. Close dialog to leave. Host can choose guest suggestions. Tests: `python -m unittest -v` inside server directory.


### v10 room blocking
New v10 rooms require a randomly generated installation token scoped to the configured server endpoint. The host can block an installation for the lifetime of its room. It removes all matching active sessions and denies rejoin with that token. Tokens are not sent to room members; they are not user accounts and can be reset. Old room clients cannot join identity-required rooms. Upgrade the server alongside the Android client.

### v15 shareable playlist snapshots
The same server supports `POST /v1/playlists/create` with `{ "name": "Playlist", "tracks": ["abcdefghijk"] }`, returning a random `code` and private `revoke` token. `GET /p/<code>` returns an escaped browser-readable list of public music links; `GET /p/<code>/json` returns the snapshot. `POST /v1/playlists/delete` requires code and revoke token. Only valid public video IDs, 1–100 items, max 100-character playlist title. No local paths/audio/credentials. Links expire in 7 days or on restart. Anyone holding a link can view it. The app requires trusted HTTPS server origin (no path prefix). No hosting is included; use the same hardened reverse-proxy guidance as rooms, particularly rate limiting on creation. Test with `python -m unittest -v`.

## V17 shared timestamp comments
The `/v1/comment_add`, `/v1/comment_list`, and `/v1/comment_delete` POST routes require existing room code and membership token. Only approved members can use them. `comment_add` accepts a public 11-character `video`, integer `position` in milliseconds (0–86400000), `text` (up to 250 characters), and `reaction` (empty, heart, star, fire). The latest 30 comments for a video are returned by `comment_list`; deletion by comment ID is allowed for the author or current host. There is a maximum of 200 comments per room, no persistence, and no public/global comment feed. Avoid personal or sensitive information. Room expiry or process restart clears the comments. Run `python -m unittest discover -v` to exercise server tests.

Version 18: optional numeric `speed` (0.5–2.0, default 1.0 for older clients) on `publish`. The `state` track position is extrapolated at the published speed up to the existing 15-second stale threshold. Clients estimate network delay separately. No audio or account cookies are sent. Use the updated server for speed-aware sync.

### Optional lyrics community votes (v20)
POST `/v1/lyrics/vote` accepts `lyric` (64 lowercase hex digest of public video ID + newline + normalized lyric version), `voter` (64 lowercase hex random secret per server), and optional `value` (1 up, -1 down, 0 remove; omitted to read). Returns up/down/mine counts. The command-line server persists votes in SQLite via `--votes-db`, default `lyric-votes.sqlite3`. Use a trusted HTTPS server. Never publish tokens or the database; restrict filesystem permissions, apply reverse-proxy request rate limiting and do not use this as a public abuse-resistant voting platform. No lyric text or audio is uploaded.

### v24 room timing
`publish` accepts optional integer `sampleAgeMs` (0–2000); while playing, the server advances the received position by that estimate times playback speed. Older clients omit the field. The server uses a monotonic clock for elapsed time. Clients still need trusted HTTPS and synchronization remains approximate.
